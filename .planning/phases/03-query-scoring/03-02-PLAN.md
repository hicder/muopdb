  <name>Task 1: Create TopKSelector utility</name>
  <files>rs/index/src/bm25/topk.rs</files>
  <action>Create `rs/index/src/bm25/topk.rs` with efficient Top-K selection:

1. **TopKSelector** struct:
   - Generic over the item type `T`
   - `k: usize` - number of top items to select
   - `heap: BinaryHeap<Reverse<(f32, T)>>` - min-heap storing (score, item) pairs
     - Uses `Reverse` to make it a min-heap (smallest score on top)
     - This allows O(1) access to the current K-th highest score

2. **new(k: usize) -> Self** constructor:
   - Initialize empty BinaryHeap with capacity k
   - Store k for bounds checking

3. **offer(&mut self, item: T, score: f32)** method:
   - If heap size < k: push item with score
   - If heap size == k and score > top().score:
     - pop the smallest (current K-th)
     - push the new higher-scoring item
   - This maintains exactly k highest-scoring items seen so far

4. **into_sorted_vec(self) -> Vec<T>** method:
   - Drain heap into vector
   - Sort by score descending (highest first)
   - Return items in rank order (1st, 2nd, 3rd, ...)

5. **current_min_score(&self) -> Option<f32>** method:
   - Returns the current K-th highest score (minimum in heap)
   - Used for early termination optimization (if we know no remaining docs can beat this score)

6. **len(&self) -> usize** method:
   - Current number of items in heap (may be < k if fewer matches)

Use `std::cmp::Reverse` for min-heap behavior. The heap stores tuples of (score, point_id) where score is used for comparison. Import from std::collections::BinaryHeap.</action>

2. Add **top_k_search()** method to Bm25Searcher:
   ```rust
   pub fn top_k_search(&self, query: &Bm25Query) -> Result<Bm25SearchResults>
   ```
   - Same signature as search() but uses TopKSelector for efficient ranking
   - Look up UserBm25StatsView for query.user_id
   - Tokenize query.text into query terms
   - Create TopKSelector with capacity query.max_results
   - For each query term:
     - Get posting list from MultiTermIndex
     - For each document in posting list:
       - Compute BM25 score for this (doc, term) pair
       - Offer (point_id, accumulated_score) to TopKSelector
   - Convert TopKSelector results to Bm25SearchResults
   - Results are already sorted by score descending

3. **Optimization - incremental scoring**:
   - Instead of computing all term scores then selecting top K:
   - Use a HashMap<u32, f32> to accumulate scores per document as we process each term
   - After processing all terms, offer each (doc, total_score) to TopKSelector
   - This is O(T × D) where T = num_terms, D = avg docs per term

4. **Update existing search() method**:
   - Make search() call top_k_search() for consistency
   - Or keep both: search() returns all matches, top_k_search() uses efficient selection
   - Document the difference: search() = all results, top_k_search() = optimized K-best

The key insight: we must aggregate scores across all query terms BEFORE selecting top K, because a document matching multiple terms gets a higher total score than single-term matches.</action>
